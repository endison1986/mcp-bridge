# mcp-bridge 配置文件与聚合端点设计（草案，待审查）

状态：已实现（v0.2.0）。
目标：用一个 JSON 配置文件替代全部命令行参数，并让 AI 客户端通过一个聚合端点使用所有已配置的 MCP 服务。

## 1. 设计原则

1. **白名单**：只有配置文件中列出的服务才可被外部访问。服务器上其他监听端口的 MCP 服务一律不暴露。
2. **单一入口**：客户端只需要配置一个 URL，即可使用所有已启用的服务。
3. **单一来源**：启动只需要 `mcp-bridge --config mcp-bridge.json`，命令行参数只保留 `--config`。
4. **安全默认开启**：鉴权默认开启；关闭时启动日志给出明显警告。

## 2. 配置文件示例

```json
{
  "mode": "mixed",
  "listen": "0.0.0.0:8080",
  "security": {
    "enabled": true,
    "client_auth": {
      "type": "bearer",
      "token": "${MCP_BRIDGE_CLIENT_TOKEN}"
    },
    "agent_token": "${MCP_BRIDGE_AGENT_TOKEN}"
  },
  "aggregate": {
    "path": "/mcp",
    "tool_separator": "__"
  },
  "servers": {
    "shell": {
      "command": ["npx", "-y", "shell-exec-mcp"],
      "env": {},
      "enabled": true
    },
    "computer": {
      "command": ["npx", "-y", "computer-use-mcp"],
      "enabled": true
    },
    "filesystem": {
      "command": ["npx", "-y", "filesystem-mcp"],
      "enabled": false
    },
    "local-http": {
      "url": "http://127.0.0.1:3000/mcp",
      "enabled": true
    }
  }
}
```

### 2.1 顶层字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `mode` | 是 | `relay`、`agent` 或 `mixed` |
| `listen` | relay / mixed 必填 | relay 监听地址，例如 `0.0.0.0:8080` |
| `relay` | agent 必填 | relay 的 WebSocket 地址，例如 `wss://relay.example.com/agent/ws` |
| `agent_id` | agent 必填 | agent 标识 |
| `security` | 否 | 安全配置，见第 3 节 |
| `aggregate` | 否 | 聚合端点配置，见第 4 节 |
| `servers` | 是 | 服务列表，只有这里列出的服务才会被访问 |

### 2.2 服务字段（servers 下的每一项）

每个服务必须且只能指定 `command` 或 `url` 之一。

| 字段 | 说明 |
|---|---|
| `command` | 字符串数组，由 mcp-bridge 启动子进程，并通过 stdio 与之通信 |
| `url` | 已在运行的 MCP 服务的 HTTP 地址（Streamable HTTP） |
| `env` | 仅 `command` 使用，子进程额外的环境变量 |
| `headers` | 仅 `url` 使用，每个发往该服务的请求都会带上这些 HTTP 头（如 `Authorization`） |
| `enabled` | 默认 `true`。设为 `false` 时该服务不加载，也不会出现在聚合端点中 |

环境变量引用：字符串中的 `${NAME}` 会在启动时替换为对应的环境变量，缺失时启动失败。配置文件本身不应包含明文密钥。

## 3. 安全配置（security）

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 关闭后，聚合端点和 agent 连接都不再校验 token，启动时输出警告 |
| `client_auth.type` | `bearer` | `bearer`：请求头 `Authorization: Bearer <token>`；`path`：URL 中带 token，例如 `/mcp/<token>`；`none`：不鉴权 |
| `client_auth.token` | 必填（type 不为 none 时） | 客户端 token，启动时检查长度，少于 32 个字符则拒绝启动 |
| `agent_token` | 必填（mode 为 relay / mixed 时） | agent 连接 `/agent/ws` 所需的 token |

说明：
- 三种鉴权方式都可以在配置中切换，默认使用 `bearer`。
- `path` 方式下 token 会出现在 URL 中，可能被记录在代理日志里，因此不推荐在公网使用。

## 4. 聚合端点（aggregate）

路径默认 `/mcp`，客户端只配置这一个地址。

### 4.1 支持的方法

- `initialize`：返回服务器信息和 `tools` 能力。
- `tools/list`：合并所有已启用服务的工具列表，并按前缀规则重命名。
- `tools/call`：解析工具名中的前缀，转发给对应服务，并把原始工具名传给后端。
- `ping`、`notifications/*`：直接响应或忽略。

其他方法返回 JSON-RPC 错误 `-32601 method not found`。

### 4.2 工具名前缀

- 格式：`{服务名}{tool_separator}{工具名}`，默认分隔符为 `__`。
- 例如 `shell__exec`、`filesystem__read_file`。
- `tool_separator` 只允许字母、数字、下划线和短横线，因为部分客户端不接受 `.`。
- 设置为空字符串时关闭前缀；如果两个服务存在同名工具，启动时报错，不会静默覆盖。

### 4.3 stdio 服务的生命周期

- 启动时为每个启用的 `command` 服务创建子进程，完成 `initialize` 握手并缓存工具列表。
- 子进程异常退出时自动重启，并记录日志。
- 工具列表变化（`notifications/tools/list_changed`）时刷新缓存。

## 5. 各模式下的行为

| 模式 | 本地服务 | 聚合端点 | 外部 agent |
|---|---|---|---|
| `relay` | 无 | 聚合所有已连接 agent 的服务（待确认，见第 7 节） | 接受 |
| `agent` | 本机 `servers` | 本机聚合端点，由 relay 转发访问 | 连接 relay |
| `mixed` | 本机 `servers` | 直接在本进程内聚合，不经过 WebSocket | 接受 |

## 6. 启动方式

```
mcp-bridge --config mcp-bridge.json
```

命令行只保留 `--config`（可选，默认 `./mcp-bridge.json`）和 `--check`（只校验配置、不启动）。
